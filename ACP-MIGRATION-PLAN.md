# План: общение с агентами через ACP + терминал для человека

Статус: черновик для обсуждения. Дата: 2026-09-28.

## 0. Принятые решения

1. **Остаёмся на Node/Electron.** Проблемы не в языке, а в том, что агентом управляем через PTY
   (печатаем промпт, ждём таймеры, отдельно жмём Enter). Rust/Tauri — отложенное решение: вернёмся,
   если размер/память станут реальной проблемой. Чтобы это было возможно — держим чистую границу
   «UI ⇄ бэкенд» (понятные сообщения, никакой логики агентов во фронте).
2. **Агенты — через ACP (Agent Client Protocol).** Агент — дочерний процесс, JSON-RPC по stdio.
   Один формат для Claude Code (адаптер `claude-agent-acp`), Codex (`codex-acp`), Gemini CLI и др.
3. **Свой MCP-сервер Plangent.** Подключается к каждой ACP-сессии. Даёт агентам инструменты
   `complete_step`, `request_help` и т.д. — явный сигнал «сделал / застрял» вместо Stop-хука и
   слежения за чекбоксами. Расширяется (ревью, вывод терминала, …). Набор инструментов зависит от роли сессии.
4. **Терминал остаётся — но только для человека.** Обычные шеллы в папке проекта (`npm run dev`, `git`, …).
   Никакой логики агентов в PTY.

## 1. UX

### 1.1 Навигация

```
Сайдбар: проекты (с бейджем «ждёт вас: N») · Настройки
Проект:  [Агенты] [Терминал] [Задачи] [Инструкции] ...
Задача:  [План] [Выполнение]
```

- Текущая вкладка проекта «Терминал» (быстрый запуск агента) делится на две:
  **«Агенты»** — чаты с агентами, **«Терминал»** — шеллы.
- Бейдж в сайдбаре у проекта: сколько сессий «ждут вас» (запрос разрешения, `request_help`,
  конец обсуждения). Если окно не в фокусе — системное уведомление Electron.

### 1.2 Вкладка «Терминал»

```
┌────────────────────┬──────────────────────────────────────────┐
│ ● dev-server       │ PS D:\projects\app> npm run dev           │
│ ○ git              │   VITE ready in 312 ms                    │
│ ◌ build (exit 1)   │   ➜ Local: http://localhost:5173/         │
│                    │                                           │
│ [+ Новый терминал ▾]│                                          │
└────────────────────┴──────────────────────────────────────────┘
```

- Слева список открытых терминалов, под списком кнопка **«+ Новый терминал»**.
  Выпадашка `▾`: выбор шелла (PowerShell / cmd / Git Bash / …) и позже — скрипты из `package.json`.
- Индикатор: ● процесс работает, ○ простаивает (шелл), ◌ завершился (с кодом).
- Двойной клик — переименовать. Контекстное меню: переименовать, перезапустить, очистить, закрыть.
- Шелл стартует в `repo_path` проекта. Имя по умолчанию — «Терминал N», после первой команды
  можно автопереименовать по команде (опционально).
- Терминалы живут, пока открыто приложение: переключение вкладок/проектов их не убивает.
  Закрытие терминала убивает **всё дерево процессов** (важно на Windows: `npm run dev` оставляет детей).
- Горячие клавиши: `Ctrl+Shift+\`` — новый терминал; `Ctrl+C/V` — копировать/вставить как в VS Code.
- Перетаскивание файла в терминал вставляет путь (уже есть).

### 1.3 Вкладка «Агенты» (чаты)

```
┌──────────────────────┬────────────────────────────────────────────────┐
│ [+ Новый чат ▾]      │ Claude · opus · ● думает               [■ Стоп] │
│                      ├────────────────────────────────────────────────┤
│ ● Рефакторинг auth   │  Вы: переделай авторизацию на JWT               │
│   Claude · думает    │                                                │
│ ! Почини тесты       │  Claude: Посмотрю текущую реализацию.           │
│   Codex · ждёт вас   │  ▸ Прочитал server/auth.ts                      │
│ ○ Вопрос по API      │  ▸ Правка server/auth.ts  (+24 −9)  [дифф]      │
│   Claude · готов     │  ┌ Разрешить команду `npm test`? ─────────────┐ │
│                      │  │ [Разрешить] [Всегда в этом чате] [Отклонить]│ │
│                      │  └────────────────────────────────────────────┘ │
│                      ├────────────────────────────────────────────────┤
│                      │ ┌────────────────────────────────────────────┐ │
│                      │ │ Сообщение… (@файл, /команда)               │ │
│                      │ └────────────────────────────────────────────┘ │
│                      │ 📎  Claude ▾  opus ▾        [Отправить ⏎]      │
└──────────────────────┴────────────────────────────────────────────────┘
```

**Список чатов (слева):** название (автоматически из первого сообщения, можно переименовать),
агент, статус. Кнопка **«+ Новый чат»** — выбор агента/модели (по умолчанию агент проекта).

**Лента сообщений:**
- Ваши сообщения и ответы агента (markdown, подсветка кода, текст приходит потоком).
- «Размышления» — свёрнутый блок.
- Действия агента — компактные строки: `▸ Прочитал файл`, `▸ Правка файла (+24 −9)` — раскрывается в дифф,
  `▸ Команда npm test` — раскрывается в вывод. Статус действия: выполняется / готово / ошибка.
- План агента (ACP `plan`) — чеклист, обновляется на месте.
- Запрос разрешения — карточка с кнопками **Разрешить / Всегда в этом чате / Отклонить**.
  Пока не ответили — чат в статусе «ждёт вас».

**Поле ввода:**
- `Enter` — отправить, `Shift+Enter` — новая строка, авто-рост по высоте.
- `@` — автодополнение файлов проекта; вставка/перетаскивание файлов и картинок.
- `/` — команды, которые сообщил агент (ACP `available_commands`).
- Пока агент работает — кнопка **Стоп** (`session/cancel`). Написанное во время работы сообщение
  встаёт **в очередь** (видно «в очереди», можно отредактировать/удалить) и уходит, когда агент закончит ход.
- Агент/модель выбираются при создании чата; смену модели внутри чата — если агент поддерживает (см. открытые вопросы).

**Статусы сессии (единые везде — в чатах, в плане, в сайдбаре):**

| Статус | Значок | Когда |
|---|---|---|
| Думает | ● синий пульс | идёт ход агента |
| Ждёт вас | ! оранжевый | запрос разрешения, `request_help`, закончено обсуждение |
| Готов | ○ | ход закончен, можно писать дальше |
| Завершён | ✓ | пункт плана выполнен (`complete_step`) |
| Ошибка | ✕ красный | процесс агента упал / ошибка протокола |

История чатов хранится в БД — после перезапуска приложения ленту видно всегда; продолжить
разговор можно, если агент поддерживает `session/load`, иначе — «Начать новый чат с контекстом»
(краткое резюме прошлого как первое сообщение).

### 1.4 Задача: вкладка «План»

- Составление плана — это **чат** с агентом-планировщиком справа от плана (вместо терминала).
- Агент пишет план **как сейчас — обычным файлом плана в репозитории**; Plangent следит за файлом
  (существующий `plan-file.ts`) и обновляет план слева на лету. Файл можно открыть в своём редакторе.
  MCP для записи плана не используется.
- Кнопка «✓ Утвердить план» — как сейчас.

```
┌──────────────────────────────┬──────────────────────────────┐
│ План (3 шага)                │ Чат планирования · Claude     │
│ ☐ p1 Модель данных           │ ...                           │
│ ☐ p2 API                     │                               │
│ ☐ p3 UI                      │ [Сообщение…]                  │
│ [✓ Утвердить]                │                               │
└──────────────────────────────┴──────────────────────────────┘
```

### 1.5 Задача: вкладка «Выполнение» (master–detail)

```
┌──────────────────────────────────┬──────────────────────────────────┐
│ Очередь                 [▶ Старт] │ p2 · API · Codex · ! ждёт вас    │
│ ✓ #1 p1 Модель данных   Claude   │ ┌ Агент просит помощи ─────────┐ │
│ ! #2 p2 API             Codex    │ │ «Нет доступа к схеме БД,     │ │
│   «Нет доступа к схеме БД…»      │ │  где взять миграции?»        │ │
│ ◌ #3 p3 UI   (обсудить)  Claude  │ └──────────────────────────────┘ │
│                                  │ …лента сессии…                   │
│ [+ Добавить шаги в очередь]      │ [Ответить агенту…]               │
│                                  │ [✓ Принять шаг] [↻ Перезапуск]   │
└──────────────────────────────────┴──────────────────────────────────┘
```

- Слева — очередь (как сейчас: шаги, агент, режим, «одновременно», «пауза после»).
  У каждой строки — статус из таблицы выше; для «ждёт вас» — одна строка причины прямо в списке.
- Клик по строке открывает справа **ту же ленту чата**, что и во вкладке «Агенты».
  Можно в любой момент открыть работающий шаг, посмотреть, что он делает, и написать ему.
- Действия в правой панели: **Ответить агенту** (поле ввода), **Принять шаг** (вручную пометить
  выполненным), **Перезапустить**, **Отменить**.
- Режим **«обсудить»** (`review_first`) ложится естественно: сессия стартует с промптом «обсуди шаг,
  ничего не меняй», по окончании хода — статус «ждёт вас»; кнопка **«Выполнить»** отправляет
  в ту же сессию «выполняй» — весь контекст обсуждения сохраняется.
- Если агент закончил ход, но не вызвал ни `complete_step`, ни `request_help` — статус
  «ждёт вас» с причиной «агент остановился без отчёта».

### 1.6 Ревью (этап 5)

- В очереди опция на шаг/на всю очередь: **«Ревью после шага»** + выбор агента-ревьюера
  (можно другого: Codex проверяет Claude).
- В правой панели шага появляется вкладка **«Ревью»**: список замечаний (файл:строка, важность,
  текст), вердикт. Замечания также показываются на диффе.
- `changes_requested` → замечания уходят исполнителю в его сессию → повторное ревью.
  После N кругов (настройка, по умолчанию 2) — «ждёт вас».

## 2. Архитектура

### 2.1 Сервер

```
server/
  core/
    agent-sessions/          # НОВОЕ: доменная логика сессий агентов
      acp-host.ts            # запуск процесса агента, ACP-клиент, жизненный цикл
      sessions.ts            # репозиторий сессий и событий (SQLite)
      permissions.ts         # политика разрешений (ask / allow-edits / allow-all)
      prompt-queue.ts        # очередь сообщений пользователя, пока идёт ход
    orchestration/           # переходит с PTY на agent-sessions + MCP-сигналы
  infrastructure/
    mcp/                     # НОВОЕ: MCP-сервер Plangent (инструменты по ролям)
    terminal/                # только шеллы для человека (без агентской логики)
    http/routes/             # + agent-sessions, terminals
```

- **ACP-клиент:** официальное TS SDK (`@agentclientprotocol/sdk` — проверить актуальное имя пакета).
- **Процессы:** один процесс агента на сессию (проще, изоляция). Позже можно переиспользовать
  процесс для нескольких сессий, если агент это поддерживает.
- **Поток событий:** ACP `session/update` → нормализованное событие → запись в БД → broadcast
  в UI по существующему WebSocket. Переход на Electron IPC — отдельно, позже (не смешиваем с этим планом).
- **Агенты в БД:** поле `protocol: 'acp' | 'pty'` (на переходный период) + команда/аргументы ACP-адаптера.
  Пресеты: Claude, Codex, Gemini (команды уточнить на этапе 0).
- **Разрешения** — см. 2.2. Флаги вида `--dangerously-skip-permissions` больше не нужны:
  все запросы разрешений приходят в Plangent, и он отвечает по политике сессии.

### 2.2 Разрешения

| Где | Режим по умолчанию | Как |
|---|---|---|
| Чат (вкладка «Агенты») | **Спрашивать** | Переключатель у поля ввода, как в Zed: «Спрашивать» / «Разрешать правки» / «Без вопросов»; меняется посреди чата |
| Выполнение шага плана | **Без вопросов** | Plangent сам отвечает «разрешить» на `request_permission`; все действия видны в ленте шага |
| Шаг в режиме «обсудить» | **Только чтение** | Режим «план» агента (у Claude есть), если поддерживается; иначе — отклонять правки/команды до «Выполнить» |

- Если агент поддерживает режимы (ACP `session/set_mode`, например Default / Accept Edits / Bypass
  у Claude) — включаем соответствующий режим; иначе Plangent отвечает на запросы сам.
- **Страховка:** список опасных команд в настройках проекта (по умолчанию `git push --force`,
  `git reset --hard`, `rm -rf`, `git clean -fd`, …). Даже в режиме «без вопросов» такой запрос
  переводит сессию в «ждёт вас» с карточкой «Агент хочет выполнить …».
  Ограничение: срабатывает только когда агент спрашивает разрешение — в режиме Bypass самого агента
  запросы не приходят, поэтому для шагов плана предпочитаем автоответ Plangent, а не Bypass (проверить на этапе 0).

### 2.3 MCP-сервер Plangent

- **Ничего не устанавливается и не обновляется вручную:** это часть кода Plangent, стартует вместе
  с приложением и обновляется вместе с ним. Plangent сам передаёт его адрес агенту при создании
  каждой ACP-сессии (`session/new` → `mcpServers`). Пользовательские MCP агента (из его собственных
  настроек) продолжают работать как раньше.
- Работает внутри процесса сервера, транспорт HTTP на `127.0.0.1`; каждой сессии —
  свой токен (по нему сервер знает сессию, роль, задачу, шаги). Если агент не поддерживает
  HTTP-MCP — маленький stdio-прокси скрипт.
- Инструменты по ролям:

| Роль | Инструменты |
|---|---|
| исполнитель шага | `complete_step(summary)`, `request_help(question)`, `report_progress(note)` |
| планировщик | пока не нужны — план пишется в файл |
| ревьюер (этап 5) | `get_review_context()`, `add_finding(file, line, severity, message)`, `submit_review(verdict)` |
| все (позже) | `get_terminal_output(terminalId)`, `get_task()` |

### 2.4 Авторизация агентов

- Plangent **не хранит ключей и не авторизует сам**. ACP-адаптер запускает настоящий CLI агента,
  который использует свой собственный вход:
  - Claude — вход Claude Code (`claude` → `/login`, подписка Pro/Max) или `ANTHROPIC_API_KEY`;
  - Codex — `codex login` (аккаунт ChatGPT) или API-ключ;
  - Gemini — вход Google-аккаунтом или API-ключ.
- ACP сообщает, что агент не авторизован, и перечисляет способы входа (`authMethods`, `authenticate`).
  UI показывает в чате карточку **«<Агент> не авторизован → [Войти]»**; кнопка открывает вкладку
  «Терминал» с командой входа (`claude /login`, `codex login`, …). После входа — «Повторить».
- API-ключи, если нужны, задаются как сейчас — через `env` агента в настройках.
- На этапе 0 проверить, что вход по подписке работает через адаптеры, и сверить актуальные
  условия провайдеров об использовании подписки в сторонних программах.

### 2.5 Данные (SQLite)

- `agent_sessions`: id, project_id, task_id?, step_ids?, role (`chat`/`planner`/`executor`/`reviewer`),
  agent_id, model, acp_session_id, title, status, created_at, updated_at.
- `agent_session_events`: session_id, seq, type, payload (JSON), created_at.
  Потоковые куски текста склеиваются в одно событие по завершении сообщения, чтобы не раздувать БД.
- `review_findings` (этап 5).
- Существующие `runs` связываются с `agent_sessions` (run ↔ сессия).

### 2.6 Клиент

```
client/src/features/
  agent-chat/     # НОВОЕ: ChatView, лента, карточки действий, поле ввода, стор сессий
  terminal/       # НОВОЕ: список терминалов, TerminalPane, стор терминалов
  projects/       # вкладки «Агенты» и «Терминал» используют публичный API двух фич выше
  tasks/          # «План» и «Выполнение» используют ChatView из agent-chat
```

`TaskView.vue` (1600 строк) при переходе на master–detail разбить на компоненты:
`PlanPanel`, `ExecutionQueue`, `StepDetailPanel`.

## 3. Этапы

Каждый этап заканчивается рабочим приложением; старый PTY-режим агентов живёт до этапа 6.

### Этап 0. Проверка (spike), 1–2 дня
- Запустить на Windows адаптеры Claude и Codex через ACP из простого скрипта.
- Проверить: стриминг, tool calls с диффами, `request_permission`, `session/cancel`,
  `session/load`, подключение HTTP-MCP, выбор модели/усилия рассуждений (в т.ч. смена модели
  посреди чата), режимы разрешений (`session/set_mode`: доступные режимы, приходят ли запросы
  при автоответе), большие промпты, вход по подписке (Claude Pro/Max, ChatGPT) и карточка «не авторизован».
- Результат — короткая таблица возможностей по агентам в этом файле. Решение go / no-go.

### Этап 1. Терминал для человека (независим от ACP)
- `features/terminal`: вкладка «Терминал» по макету 1.2, кнопка «+», выбор шелла, переименование, закрытие.
- Сервер: шеллы без агентской логики, убийство дерева процессов на Windows.
- Переход `xterm` → `@xterm/xterm` (+ `@xterm/addon-fit`, WebGL-аддон).
- Текущий быстрый запуск агента временно переезжает во вкладку «Агенты» (на старом PTY).

### Этап 2. ACP-ядро на сервере
- `core/agent-sessions`: запуск, ACP-клиент, события, БД, очередь сообщений, отмена, разрешения.
- HTTP/WS API: создать сессию, отправить сообщение, отменить, ответить на разрешение, получить историю.
- Настройки агента: протокол ACP + пресеты.

### Этап 3. Чат в UI
- `features/agent-chat` по макету 1.3; вкладка «Агенты» в проекте на ACP.
- Бейдж «ждёт вас» в сайдбаре, системные уведомления.

### Этап 4. План и выполнение на ACP + MCP
- MCP-сервер Plangent с ролью исполнителя (план по-прежнему пишется в файл).
- Оркестратор: запуск шагов через agent-sessions; статусы из `complete_step` / `request_help` /
  конца хода; убрать зависимость от Stop-хука и таймеров.
- UI: «План» с чатом планирования (1.4), «Выполнение» master–detail (1.5), разбиение TaskView.

### Этап 5. Ревью
- Роль ревьюера, инструменты ревью, вкладка «Ревью» в панели шага, цикл исправлений.

## 4. Решения по вопросам (2026-09-28)

1. **Терминал — вкладка сверху** в проекте, как сейчас и как в похожих программах. Нижней панели нет.
2. **План пишется в файл, как сейчас** — видно в редакторе и в UI на лету. MCP только для сигналов
   «сделал / нужна помощь» (и позже ревью). MCP встроен в приложение, ничего ставить не нужно.
3. **Смена модели посреди чата** — делаем, если адаптер поддерживает (выяснить на этапе 0);
   иначе модель выбирается при создании чата.
4. **Web-версия и Docker остаются**, пока не требуют отдельной работы. Чат идёт через тот же
   HTTP/WebSocket-сервер, поэтому в вебе заработает сам собой.

5. **Разрешения:** в чате — как в Zed (спрашивать, переключатель режима); при выполнении плана —
   без подтверждения, со страховкой на опасные команды; «обсудить» — только чтение. Подробно в 2.2.
